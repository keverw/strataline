## Unreleased

This release hardens the local development database server around process identity and lifecycle races. A PID number alone is no longer treated as proof that a process is this cluster's PostgreSQL server. It also stops a callback you supply from being able to end your process by failing.

- **Breaking:** `stop()` no longer exits the host process, the library no longer installs operating-system signal handlers, `onExit` is now only a notification for an unrequested PostgreSQL exit, startup refuses ambiguous PID state, a `start()` overlapping another lifecycle call is refused rather than queued, `dataDir` is resolved to an absolute path, shutdown uses PostgreSQL's fast-to-immediate escalation, the PID file now contains structured JSON that older Strataline versions cannot read, `MutableLogger` forwards lines untouched rather than prefixing them, `TestDatabaseInstance.getCredentials()` reports `127.0.0.1` rather than `localhost`, `TestDatabaseInstance.stop()` throws when it could not stop the server rather than resolving and is refused while a start is in flight, a second `TestDatabaseInstance.start()` is refused rather than run beside the first, every entry point takes the structured `Logger` in place of a tagged logger function, the three per-surface console logger factories are replaced by a single `createConsoleLogger` that names the sources to quiet, the whole logging API moved off `strataline/migration` to a `strataline/logger` entry point of its own, and the new `{ pg: false }` filter no longer hides PostgreSQL's warnings and errors.

**Process Identity**

- Added `getLocalDevDBServerStatus()` and exported the PID utilities from `strataline/local-dev-db-server`. Status distinguishes verified, stale, and `indeterminate` records so callers can refuse destructive work when identity cannot be established.
- Verification uses the process command, start time, current boot, data directory, and owning uid where the platform provides them. Linux uses `/proc`, macOS uses `ps`, and Windows uses one PowerShell CIM query. The probes that shell out are bounded, since they run synchronously and a hung one would block the event loop where no timer could recover it. A probe that times out reads as no answer, which is the cautious direction.
- An optional connection probe can ask PostgreSQL for its own `data_directory` when file and process evidence cannot decide. The configured development user receives `pg_read_all_settings` so it can answer that query.
- Live process identity takes precedence over wall-clock heuristics, preventing clock adjustments and restored virtual-machine snapshots from making a running server look as though it predates the current boot.
- A probe that could not run now says why. `ps` missing from PATH, PowerShell refused by execution policy, and a probe killed at its timeout all used to read as the same absent value as a platform that simply has no such probe, so a refusal said only that identity could not be established. `VerifyPidResult` and `DevDBServerStatus` now carry a `probeFailures` list, and the same text is appended to `reason`, so the message a person acts on names the check that failed and its error code. A reading the platform never offered, such as a uid on Windows, is not a failure and does not appear there.
- A probe supplied through the `probes` option can no longer end a status check by throwing, including the boot-time read each status path makes before it verifies anything. The built-in probes never throw, but that option is public and an injected one is somebody else's code, so a throw used to escape `verifyPid` and take `start()` with it. A throw is now the absent reading it should have been, and is recorded like any other probe failure. Liveness is the exception and degrades to "something may be there" rather than to "gone", since only the second licenses deleting a record.

**Starting and Stopping**

- A new cluster is initialized with an explicit superuser rather than one named after whoever ran `initdb`, and the dev server connects as that name. Working the name out independently meant asking who this process is and being right on every platform and runtime, and where the answer was wrong every start failed with `role "..." does not exist` against a database it had just created. An inherited `USERNAME`, a container that pins it, `su` without a login shell, and a process launched under other credentials all produce that. A name chosen here cannot disagree with itself, and it leaves the cluster independent of the account that happened to create it. A data directory from an earlier version keeps its own superuser and still works, since readiness tries both and remembers the one that answers. The dev server also now prefers the operating system's idea of the current user to the environment's, which is the same reasoning applied to the fallback.

- **Breaking:** startup now refuses an unreadable, changing, unclaimable, foreign, or otherwise ambiguous PID record instead of signaling a PID or deleting a record it cannot establish as stale. Record removal uses a rename-based claim protocol so a replacement record is never deleted by an earlier startup.
- **Breaking:** shutdown now escalates through `SIGINT`, `SIGQUIT`, and `SIGKILL`. This avoids PostgreSQL's `SIGTERM` smart-shutdown mode, which can wait indefinitely for clients. Each step has its own budget, and `SIGINT` gets much the largest one, because it is the step that ends cleanly and its shutdown checkpoint takes as long as the database is dirty. A server that ignores every signal is given about 42 seconds in total before `stop()` reports failure. Windows uses `pg_ctl kill` for PostgreSQL signal semantics and Node for the final hard kill, and that call is bounded too, so a `pg_ctl` that never returns cannot outlast the shutdown it was part of.
- `stop()` and `shutdown(signal)` resolve only after PostgreSQL has stopped and PID-record cleanup has finished. They reject failed shutdowns, never exit the host, and never call `onExit`.
- **Breaking:** calling `start()` while starting or stopping, or calling `stop()` or `shutdown(signal)` while starting, now rejects with a descriptive error instead of queueing conflicting background operations. A second `stop()` or `shutdown()` still joins the shutdown already running. Stopping is the forgiving one on purpose, because the two refusals fail in opposite directions: a `start()` that rejects leaves no server, while a `stop()` that rejected would leave a postmaster holding the port and the data directory, which is what the call exists to prevent.
- Added `getLifecycleState()`, returning `"stopped"`, `"starting"`, `"running"`, `"stopping"`, or `"unstoppable"` as `DevDBLifecycleState`. The refusals above throw, and a call that throws is not a way to find out, so a host with more than one route into a stop had no way to tell "a shutdown is already running" from "a start is, and this call is about to throw". It also tells a joined `stop()` whether it stopped the server or waited on somebody else's shutdown, which the joined promise cannot say, and names the state a failed `start()` leaves when the partially started server outlived even `SIGKILL`, which the child's own exit status cannot distinguish from a healthy server or an absent one. It reports this instance's own view, decided the same way the guards are, and says nothing about a server left by a previous run, which remains `getLocalDevDBServerStatus()`'s question.
- A host that stops on a signal has to wait for an in-flight `start()` rather than call `shutdown(signal)` into that refusal. Startup is the longest part of a cold run and so is exactly when `Ctrl+C` lands, and a script that exits there leaves the postmaster to the synchronous `exit` hook, which only `SIGKILL`s: no shutdown checkpoint, a stale `postmaster.pid`, and leaked SysV IPC objects. The README example and the development script both show that wiring.
- Clean startup no longer waits an arbitrary two seconds after confirming that there is no previous process to stop. Shutdown already waits for a process it actually terminates.
- A data directory that already holds something other than a cluster is named as such on Windows too. `rename()` replaces an empty destination on POSIX and reports `ENOTEMPTY` for one holding anything, while Windows refuses a destination that exists at all and reports `EPERM`, so the same situation arrived under an errno the check did not know and surfaced as a bare rename error naming two paths and no cause. `EPERM` and `EACCES` now count, but only where the destination is actually there, so a genuine permission failure still reports itself. A `dataDir` that already exists and is empty is an ordinary first run, though. A `mkdir -p` in a setup script produces one, and so does the directory an earlier version's in-place `initdb` was pointed at. Windows reports the same `EPERM` for one of those, so an empty destination is now cleared and the publish retried ahead of all of that. Where the destination can be neither renamed onto nor cleared, which is what a `dataDir` that is a mount point of its own looks like, `initdb` runs inside it instead. A volume mounted there in a container puts the staging sibling on the far side of a filesystem boundary, and `rename()` will not cross one, reporting `EXDEV` on macOS and `EBUSY` on Linux. That case gives up the interruption protection above and keeps the behavior the in-place `initdb` always had, rather than losing the setup altogether. An `initdb` that fails or is interrupted there leaves what it wrote for you to clear, since the destination is the name every start against that `dataDir` aims at, and nothing here can tell a half-written cluster of its own from one another start has just finished.
- A first run that is interrupted while `initdb` is working no longer leaves a data directory that every later start refuses. `initdb` is the one unbounded step in a start, and the step a cold run spends nearly all of its time in, so it is where a `Ctrl+C` lands. Running it in place left a directory holding part of a cluster and no `postgresql.conf`, which is neither a cluster nor absent: the next start saw no config, ran `initdb` again, and `initdb` refuses a directory that is not empty, so the failure repeated until somebody deleted the directory by hand. Initialization now happens in a uniquely named sibling that is renamed into place only once it has succeeded, so the data directory only ever exists initialized. What an interruption leaves behind is that sibling, which no start ever consults, so a retry simply works. It is not removed automatically, since telling it apart from the staging directory of a start that is running right now is not something this can do safely, so an interrupted first run leaves a directory to delete at your leisure. Where the data directory already holds something that is not an initialized cluster, the error now names it and says what to check, rather than surfacing as `initdb`'s own "exists but is not empty". A `dataDir` that is a symlink is followed, so a cluster parked on another volume lands where the link points.
- Startup rejects promptly when spawning, `initdb`, readiness, or final setup fails, includes captured PostgreSQL diagnostics, and cleans up any partially started child it can still identify. Readiness retries also close every attempted connection. The readiness wait now holds to a bound of about thirty seconds: each attempt gets a short timeout of its own, so something else holding the port and accepting connections without answering no longer stretches the wait to minutes, and the error says how long it actually waited. It also polls finely at first and backs off to the old one-second interval, so a server that becomes ready in the usual few hundred milliseconds is noticed then rather than at the end of a flat second.
- A server's cleanup now runs on the child's `exit` rather than its `close`. Node emits `exit` once the process is gone and `close` once the process is gone and every stdio pipe has closed, and PostgreSQL's backends inherit those pipes, so a postmaster killed without signaling its children left orphaned backends holding them and `close` arriving late or never. Releasing the PID record, dropping the reference, and reporting an unrequested exit through `onExit` are all about the process rather than the pipes, so a crashed server could sit with its record still on disk and its death unreported. Where a startup failure has to be diagnosed, the pipes are given a bounded moment to flush first, so a message like a major-version mismatch is still carried out with the error rather than reduced to an exit code.
- Shutdown revalidates a recorded process before every signal, waits for child lifecycle cleanup without hanging forever on inherited stdio, and ignores late events from a superseded child rather than applying them to a newer server.
- `start()` decides whether a server is already running from what Node reports about the child rather than from holding a reference to it. A postmaster killed without signaling its children leaves them holding the inherited stdio pipes, which can hold back the `close` event indefinitely, and a `start()` in that window used to report the server as already running and resolve with no database behind it. It now finishes the dead child's cleanup and starts a new server.

**PID Records**

- **Breaking:** Strataline now writes a JSON PID record containing the PID, start time, absolute data directory, port, boot time, and uid. Readers continue to accept the previous bare-integer format, so upgrades are transparent, but downgrades are not. The record is published without replacing an existing one. Publication is atomic where the filesystem supports hard links, while the exclusive-create fallback can briefly expose an incomplete record that readers safely refuse. A record that arrives while this server is starting therefore refuses the start rather than being overwritten unseen, and a `pidFile` on exFAT, an SMB share, or a cloud-sync mount still starts.
- A failed startup or delayed child cleanup removes only the exact record written or examined by that lifecycle. Failed boot-time probes are retried instead of being cached as permanently unavailable.

**Host Integration**

- The dev server's setup DDL quotes the role name, database name, and password through pg's own `escapeIdentifier` and `escapeLiteral` rather than by hand. Neither a name nor a password can be a bound parameter in DDL, so all three are interpolated, and the hand-rolled version doubled a `'` in the password and did nothing at all to the identifiers. A `"` in `user` or `database` therefore closed the quoting and failed the start with a syntax error against a cluster it had just created. `TestDatabaseInstance` already used the same escapers for the one identifier it interpolates.
- **Breaking:** the library traps no `SIGINT`, `SIGTERM`, or `SIGHUP`. Hosts that want graceful signal shutdown must call `shutdown(signal)` and decide when to exit. The development script now demonstrates that wiring.
- **Breaking:** `onExit` reports only a server that dies without being asked. A script whose whole purpose is the dev server should exit from that callback, and should exit non-zero rather than forwarding PostgreSQL's own code, because a shutdown asked for from outside the process, a `pg_ctl stop` for instance, arrives there with code `0` and would report a vanished database as a clean run. Embedders can recover or carry on instead.
- The only installed `process` listener is a shared synchronous `exit` hook that force-kills surviving child processes. It is installed while at least one server owns a child, and does not accumulate across instances: one hook serves every server in the process, and it comes off when the last of them lets go. `start()` puts it on and the shutdown takes it off, so there is nothing to release by hand.

**Test Databases**

- A `TestDatabaseInstance` start that fails now rejects instead of hanging. `EmbeddedPostgres.stop()` waits for the child's `exit` event and sends a signal to provoke it, but a postmaster that has already exited fired that event before the listener was attached, and Node does not replay it, so the wait never ends. That is exactly the state a failed start leaves, so cleanup after one hung forever and the caller was handed no error at all rather than the reason PostgreSQL had already written. A port that could not be bound is how this was found, and an incompatible data directory or exhausted shared memory reached it identically. The stop is now bounded, which is safe in the case that produces it, since the process being gone is the whole reason the event never came. What the rejection carries is fixed too: `EmbeddedPostgres.start()` rejects with no value at all, so the reason lived only in the output PostgreSQL logged on the way down, and reading a message off that empty rejection produced a `TypeError` in place of the failure. A valueless rejection now becomes an error carrying what the server wrote.
- **Breaking:** `TestDatabaseInstance.stop()` now throws when the server could not be stopped, rather than resolving as though it had. It used to be fail-safe and swallow everything, so a teardown reported success over a PostgreSQL that was still holding its port and its data directory, and a caller who supplied no logger was told nothing at all. Both database surfaces now fail the same way, which is what a server's `stop()` is generally expected to do, so learning one does not teach the wrong thing about the other. Since this usually runs in an `afterAll`, a rejection fails the suite: that is intended, and `stop().catch(...)` at the call site is the way to decide otherwise.
- A stop that gives up on a cluster that is still there now keeps that server and its data directory rather than releasing them. Giving up is not the same as having stopped, and a postmaster writing its shutdown checkpoint on a loaded machine reaches the same bound as one that is wedged. Releasing it threw away the only handle to a live server and deleted the files it was still writing to. Calling `stop()` again asks the cluster afresh and finishes the job once the postmaster has gone. `start()` refuses in the meantime, since building a second cluster would leave the live one holding its port with nothing recording it.
- Overlapping lifecycle calls on one `TestDatabaseInstance` are refused or joined rather than run beside each other, the way the dev server's already were. A second `start()` is refused: the already-started check reads the connection pool, which nothing sets until the very end of a start, so two calls that overlapped both found the instance idle and both built a cluster, and the second one's server and data directory replaced the first's. That left the first postmaster reachable by nothing, since the teardown stops and deletes whatever the fields hold by then, so it outlived the run holding a port and a temporary directory with nothing recording it. A `start()` that overlaps a teardown is refused for the mirror reason: a teardown clears its pool early and then waits on the server, so the start built an entire new cluster and the teardown resumed to delete the data directory, by then the new server's. A `stop()` that overlaps a start is refused too, since a teardown cannot wait a start out. A second `stop()` still joins the first rather than throwing, because a teardown that refused would leave a server running, which is what the call exists to prevent. Two of them used to collide over one instance, both ending the same pool, so pg rejected the second with `Called end on pool more than once` and that was logged as an error which had not happened. A `start()` against an instance that is already up stays a no-op and now says so in a warning, as the dev server has always done.
- `TestDatabaseInstance.getLifecycleState()` answers the same question `LocalDevDBServer.getLifecycleState()` does, in the same words, and exists for those refusals: a call that throws on an overlap is not a way to find out which lifecycle you are in. A suite with more than one route into a teardown can ask first and tell "a stop is already running", which joins, from "a start is, and this call is about to throw". The states are one shared union rather than a copy each, exported as `LifecycleState` from both `strataline/test-db-instance` and `strataline/local-dev-db-server`, where `DevDBLifecycleState` remains as an alias of it. The narrower `isReady()` is unchanged and remains the question most callers want, whether there is a pool to query right now: `running` is the only state it reports true for.
- The test database's startup lines now carry `source: "setup"`, the way the dev server's always have, so `createConsoleLogger({ setup: false })` means the same thing whichever database you hand it to. It previously tagged none of them, so the option quieted the dev server and did nothing at all on the surface where a quiet run is most often wanted. What the startup is doing carries the source. What the instance says in its own voice does not, so naming a port, reporting that it started, and saying why something failed all survive the filter.

- `TestDatabaseInstance` now picks its automatic port from outside the host's ephemeral range, and from a random point in that window. An automatically assigned port used to come from the ephemeral range, which is also where the kernel draws the local port for outgoing connections, so one of the connections made while the database was starting could take the number before PostgreSQL bound it. The database then failed to start with "could not bind IPv4 address", intermittently and under load. On Linux the range is read from `net.ipv4.ip_local_port_range` rather than assumed, since it is a sysctl and hosts that make many outbound connections routinely widen it to cover the whole unprivileged port space. Where it is widened far enough that no window sits outside it, there is no better answer available and the previous behavior stands. That narrows the window rather than closing it, so a start that still loses the port now takes another one and tries again. The retry is cheap because `initdb` writes no port into a cluster, so it keeps the data directory it already built and only spawns a new postmaster against it. It applies only to a port Strataline chose: an explicit `port` is used as given, never searched for, and never quietly replaced. The chosen port is named in the log, and so is a retry.

- **Breaking:** the test cluster listens on IPv4 only, and `getCredentials()` reports `127.0.0.1` in place of `localhost`. embedded-postgres passes no `listen_addresses`, so the cluster took PostgreSQL's default of `localhost` and bound both `127.0.0.1` and `::1`. That is the same hazard the dev server has always pinned against: on some hosts the per-connection backends fail to set `TCP_NODELAY` on an IPv6 socket and log a `FATAL`, sometimes crashing. Binding one family also halves what a start has to acquire, since a port free on IPv4 and taken on `::1` failed the whole start. The client side is pinned to match, because a server on `127.0.0.1` and a client resolving `localhost` to `::1` is a connection refused. Anything that passes the credentials to a PostgreSQL client is unaffected. Only code comparing the host string sees the change.
- PostgreSQL's own severity is read on this surface too, so the replacement `{ pg: false }` source filter quiets routine output without also hiding the `WARNING` or `FATAL` that says what went wrong, and a start that fails for want of SysV shared memory or semaphores carries the same explanation the dev server gives. Both readers look for English severity words, so the test cluster is now initialized with `lc_messages = C` to match the dev server's, rather than taking the locale embedded-postgres detects for it. The captured output is bounded rather than accumulating a running database's whole log in memory.

**Diagnostics**

- A PostgreSQL start that fails for want of SysV shared memory or semaphores now says so in its own terms. Both exhaustions are reported by PostgreSQL as "No space left on device", which reads as a full disk and is instead a per-machine kernel limit, usually reached because objects leaked from servers that were killed rather than shut down. The thrown error now says that and names `ipcs` and `ipcrm`.

- `RunStratalineCLI` no longer replaces the reason a run failed with a message about closing its database pool. The pool is closed on the way out, and that close used to sit in a `finally`, where an `await` that rejects takes the place of whatever was already propagating. It can reject on its own account, because the CLI adopts the pool it is given, so handing it the same one twice has pg refuse the second close with `Called end on pool more than once`, and a run that had by then already failed against a closed pool reported only that. A close that fails while another error is on its way out is now logged and stood aside, so the original diagnosis is what reaches the caller. Where the run itself succeeded there is nothing to displace, and a pool that will not close is a leaked resource rather than noise, so that one still throws.

- `RunStratalineCLI` rejects a numeric environment variable that merely starts with a number, rather than silently configuring the number it starts with. `parseInt` takes a prefix and stops at the first character it cannot use, so `POSTGRES_PORT=5432oops` was accepted as `5432`, `POSTGRES_CONNECTION_TIMEOUT=4.5` as `4`, and a timeout written as `1000ms` lost its unit. The range checks could not catch any of them, since what came out was inside the range, so the pool was configured with something other than what was written and nothing said so. `POSTGRES_PORT`, `POSTGRES_MAX_CONNECTIONS`, `POSTGRES_IDLE_TIMEOUT`, and `POSTGRES_CONNECTION_TIMEOUT` now have to BE whole numbers, and a value that is not one is reported the same way one outside the range already was, naming the variable and showing what was read.

**Callbacks**

- A callback you supply can no longer end the process by failing. `onExit` and every logger this library accepts are called from places that hold no promise: an exit handler, a `setInterval` body, a pool error listener, a voided chain. A throw from any of them used to escape as an unhandled rejection, which Node terminates the process over. These callbacks are also declared `=> void`, which an `async` function satisfies, so an asynchronous implementation could fail in a way no `try` at the call site could see. Both shapes are now absorbed, and every logger is guarded once where it is supplied rather than at each of the places it is called.
- A failing logger degrades rather than going quiet. The failure is first re-reported through that same logger at its error level, since what broke is usually one level or one destination rather than the whole thing. Only when that fails too is the logger treated as unusable, and the failure goes out of band: dispatched as a cancelable `ErrorEvent` of type `error` where the host has already made `globalThis` an EventTarget, otherwise handed to `globalThis.reportError` where the runtime provides that instead, and to the console where there is neither or where nothing canceled the event. Listen with `globalThis.addEventListener("error", ...)` to receive these, and call `preventDefault()` to take responsibility and suppress the console line. Those channels are detected and never installed, since making `globalThis` an EventTarget is a decision about the whole program rather than a library's to take. Nothing is written to the console until two calls to your own logger have failed.
- A failing `onExit` is reported through the logger.
- A `Logger` that prefixes itself is now asked to, by its `createPrefixed` method rather than by whether it descends from `BaseLogger`. A wrapper or decorator around a logger used to fall through to the built-in prefixer, losing that logger's own prefixing with nothing failing, since both branches return a working logger.
- A logger wrapper no longer calls a `warn` that is not there. `Logger` declares the method, but a JavaScript caller can supply an object without it, and wrapping such a logger produced one that had `warn` and reached the one that did not. Every wrapper this library builds now falls back to `info`, so a wrapper is never worse than what it wraps.
- **Breaking:** `MutableLogger` no longer prefixes the lines it passes on. It built the `[task] [stage] ` prefix out of the caller's own fields, put it in front of the message, and then forwarded those fields as well, so a base logger that renders them, which `ConsoleLogger` does, rendered them a second time and every line came out doubled. It takes no prefix of its own, so it had nothing to add: it is a verbosity gate and now forwards what it is given untouched. Which logger renders the fields has one answer, the same one `PrefixedLogger` relies on, and it is the logger at the bottom. A base logger that ignores `task` and `stage` rather than rendering them will now see them only as fields.

- The loggers are split by role behind a shared `ForwardingLogger`. They come in two kinds: a sink renders `task` and `stage` into a prefix and writes the line, which `ConsoleLogger` does, and a forwarder gates the line, fills a field in, or wraps the call and hands it on. Rendering belongs to the sink alone, and a forwarder that also rendered is exactly the bug above. A forwarder now says what it does by returning the data to pass on or `null` to drop it, so it has nowhere to put a rendered string and cannot reintroduce that. The `warn` to `info` fallback moves there too, from three hand-written copies to one. `MutableLogger`, `PrefixedLogger`, and the internal safe logger are all built on it, and none of their constructors or behavior changed beyond what is listed above.

- **Breaking:** every entry point now takes the structured `Logger` rather than a tagged function. `LocalDevDBServer`, `TestDatabaseInstance`, and `RunStratalineCLI` used to accept `(type, message) => void`, where `type` was severity and origin crossed into one enum, spelled out differently on each of the three: `pg` and `setup` carried no severity at all, so a PostgreSQL failure and a routine startup line were both an ordinary log, and `migrate-info` was a namespace built out of a string prefix. Those come apart into the two things they were. Severity is the method called, and origin is a `source` field on the line, so `logger("migrate-error", text)` becomes `logger.error({ source: "migration", message: text })`. `DevDBLoggerFunction`, `TestDBLoggerFunction`, and `CLILoggerFunction` are gone, and the type to use is `Logger`, exported from `strataline/logger`.
- **Breaking:** `createDevDBConsoleLogger`, `createTestDBConsoleLogger`, and `createCLIConsoleLogger` are replaced by a single `createConsoleLogger`, exported from `strataline/logger` and meaning the same thing whichever surface you hand it to. It takes the sources to quiet by name, and shows everything by default:

  ```ts
  createConsoleLogger({ pg: false }); // was createTestDBConsoleLogger()
  createConsoleLogger({ pg: false, setup: false }); // was createDevDBConsoleLogger(false, false)
  createConsoleLogger({ migration: false }); // was createCLIConsoleLogger(false)
  ```

  The three were the same class with different source names compiled in, and their positional booleans were the hazard: `(pgVerbose, setupVerbose)` on one and `(pgVerbose, migrateVerbose)` on another meant identical-looking call sites did different things, with a different default in the first slot and nothing in the type system able to tell them apart. Naming the source removes the question and takes the per-surface defaults with it, so a test database that wants PostgreSQL quiet now asks for it rather than inheriting it from which factory it happened to call.

- **Breaking:** the logging API moved to its own entry point, `strataline/logger`, and `strataline/migration` no longer re-exports any of it. Logging is not a migration concern, and a caller wiring up the dev server or the test database needs it just as much, so re-exporting the same names from each surface would have been four homes for one API. Every name is an import path change rather than a removal, since all of them are still exported and still called the same thing. The full set that used to come from `strataline/migration` is `Logger`, `LogLevel`, `LogData`, `LogDataInput`, `BaseLogger`, `ConsoleLogger`, `MutableLogger`, `PrefixedLogger`, `consoleLogger`, `createPrefixedLogger`, `buildLogPrefix`, and `getErrorMessage`. Change the specifier and nothing else:

  ```ts
  // was: import { consoleLogger, type Logger } from "strataline/migration";
  import { consoleLogger, type Logger } from "strataline/logger";
  ```

  The names added this release live there too, rather than anywhere else: `createConsoleLogger`, `SourceFilterLogger`, `ForwardingLogger`, `LogSource`, and `SourceVerbosity`.

- `SourceFilterLogger` is exported alongside it, so the same filtering applies to a logger of your own rather than only to the console: `new SourceFilterLogger(myPinoAdapter, { pg: false })`. Previously the verbosity flags lived inside the bundled console logger, so supplying your own logger silently gave up any way to quiet a source.

- Quieting is routine `info` output only, and a source you did not name is always shown. So a filter written for one surface is safe anywhere: the wrong one is louder than intended, never quieter. What changes in the output itself is the label, which gains the source and drops the level it used to carry, since the level is now the console method the line lands on: `[MIGRATE-ERROR] ...` becomes `[MIGRATION] ...`, on `console.error` as before.
- Structure survives to the logger you supply. Migration lines used to be flattened into a string on the way out, so `task`, `stage`, and the error OBJECT were lost to anything but the CLI's own console. They now arrive as fields, which is what makes structured logging possible through these entry points at all.
- PostgreSQL's own severity is read out of its output. It prints `2026-09-02 19:32:50.954 MDT [64506] FATAL:  ...`, naming how bad each line is, and every one of those lines used to reach your logger at `info` regardless. A WARNING now arrives as a warning and an ERROR, FATAL or PANIC as an error. Your logger is called once per PostgreSQL message rather than once per chunk the pipe delivered, so a FATAL arrives whole and keeps the DETAIL and HINT that explain it, a routine LOG that happened to arrive alongside it stays routine, and where the server flushed decides nothing. Anything unreadable stays `info`, which is where it was before.
- Both clusters are now started with `log_line_prefix` pinned to `%m [%p] `, which is PostgreSQL's own default, so an ordinary cluster's output looks exactly as it did. It is pinned because the value otherwise comes from the data directory rather than from the binary being run, and a dev server's data directory persists between runs and can be edited. A prefix may also contain `%a`, the connecting client's own `application_name`, which is arbitrary text that would sit ahead of the severity being read. If you had set `log_line_prefix` in a dev server's `postgresql.conf`, that setting no longer takes effect.

- **Breaking:** the `{ pg: false }` option that replaces `pgVerbose: false` quiets PostgreSQL's routine output only, rather than everything it writes. A warning or an error is shown whatever the filter says, on the same reasoning that has always applied to migration verbosity: the option is for sparing you "listening on IPv4 address", not for hiding the FATAL that says why the server would not start.
- A source is optional and has no default. A line without one is the component's own voice and renders unprefixed, exactly as it did before. A source names some other thing speaking through it. The built-in names are `pg`, `setup`, and `migration`, and the type is open, so a host can add its own and the console loggers will show it rather than filter it.
- `ConsoleLogger.error` no longer prints a trailing `undefined` for an error line that carries no error object.
